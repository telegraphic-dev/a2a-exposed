# Changelog

All notable changes to the `a2a-exposed` CLI (called `a2a-over-webhook` up to 0.3.x), Worker template, control core, and skills. Versions follow [semver](https://semver.org); a `v*` tag publishes the CLI and `@a2a-exposed/control-core` to npm (see [Releases](docs/README.md#releases)).

## Unreleased

- **`announce_address` cannot reissue a revoked return token (#170).** The MCP `announce_address` tool no longer has a `reissue` input. For a peer whose return token the owner revoked, it reports `revoked` and mints nothing. A call that includes `reissue` fails with error code `reissue_owner_only`, on the connector and on `POST /owner/mcp/announce_address` (self-hosted and hosted). Reissuing stays an explicit owner action: `peer announce --to <alias> --reissue`, or `POST /owner/peers/announce` with `{ to, reissue: true }`. The tool description tells the agent that a peer's message is not a reason to announce, and the tool is no longer marked idempotent.

## 0.8.25 - 2026-10-29

No new migrations. Self-hosted inboxes need no action beyond `npx -y a2a-exposed@latest deploy`.

- **Concurrent wake saves (#174).** When two saves of the same wake settings race, the one that loses the configuration version now gets a typed `conflict` result instead of a database duplicate-key error. This also holds while the winning save's outbox delivery is still pending. Only the winning save enqueues a configuration push. Database failures still roll back the whole batch, and failed pushes stay queued for retry.

**Upgrade notes for hosted (multi-tenant) operators** (unchanged from 0.8.24; they apply if you are upgrading from 0.8.23 or earlier):

- Before deploying this Worker, confirm no tenant row has `secrets_enc IS NOT NULL` together with `UPSTREAM_` keys in `config_json`. Expect 0 rows; move any you find into the sealed envelope first.
- Roll out in this order: (1) the Worker (data-plane reader), (2) every control-plane writer, (3) only then start writing upstream secrets.

## 0.8.24 - 2026-10-29

No new migrations. Self-hosted inboxes need no action beyond `npx -y a2a-exposed@latest deploy`.

- **Tunnel Access credentials for tenant wakes (#169).** Control-core accepts a complete tunnel Access service-token pair when saving tenant wake settings. The encrypted pair stays on the same wake URL and clears when the URL changes or is removed. A partial or invalid pair is rejected before anything is stored.
- **Sealed upstream credentials (#169).** Tenant secret envelopes recognize upstream bearer and Access credentials (`UPSTREAM_TOKEN`, `UPSTREAM_ACCESS_CLIENT_ID`, `UPSTREAM_ACCESS_CLIENT_SECRET`) for hosted façade integrations. The v1 envelope format is unchanged.

**Upgrade notes for hosted (multi-tenant) operators:**

- Before deploying this Worker, confirm no tenant row has `secrets_enc IS NOT NULL` together with `UPSTREAM_` keys in `config_json`. With a sealed blob present, the new reader treats `UPSTREAM_*` as sealed-only fields and ignores plaintext copies, so such a row would lose its upstream credentials. Expect 0 rows; move any you find into the sealed envelope first.
- Roll out in this order: (1) the Worker (data-plane reader), (2) every control-plane writer, (3) only then start writing upstream secrets. Older writers drop unknown fields when they reseal, so writing upstream secrets before all writers are updated can silently remove them.

## 0.8.23 - 2026-10-29

`npx -y a2a-exposed@latest deploy` (applies migrations `0014_peer_address` and `0015_outbound_source`: a peer row can hold a verified card URL, and each outbound peer records whether the owner synced it or an address announcement created it). Existing pairings keep working unchanged.

- **Peer addresses (#162, #168).** An agent can pair before it has a public card URL. It can send right away, and replies wait on the task until it has an address. The new `peer announce (--to <alias> | --all)` command tells paired peers this inbox's current card URL over the existing pairing. A peer switches to the new address only after that card proves the same pairing identity, and only for an outbound peer that an announcement created. An announcement never repoints a peer the owner added with `peers sync`, and never changes a URL while keeping the old token. One approval sets up the return path. A revoked return token stays revoked until `peer announce --to <alias> --reissue`. The return token is never printed. On an old inbox, `peer forward --to <card-url>` answers callers with a moved pointer for a grace period (default 168 hours, at most 720) and forwards the caller's token only after the new card proves it belongs to this inbox; `peer forward --off` stops it. `status` lists paired peers with no address and announcements that are still pending. Peers that do not support address updates keep their current token and read replies from the task as before.
- **Reply delivery retries (#163, #167).** `reply` waits at most 18 seconds for delivery, with at most one agent-card request and seven seconds per request. An identical retry while delivery is still running reports that it is in flight instead of the final task state. The first recorded delivery result is kept: a late success does not replace an uncertain result, and a retry never sends the same answer twice.

## 0.8.20 - 2026-10-28

- **Reply delivery (#257).** A reply is always stored on its task. An existing task push stays the only delivery path when configured; otherwise an exact live paired peer whose outbound token is held receives one A2A message in the same context, referencing the original task. Claimed cards and tokenless or revoked peers remain stored-only. The result distinguishes delivered, stored-only, and failed delivery without exposing credentials; retries are idempotent, direct replies do not loop, and failed delivery never loses the stored answer. External delivery uses DNS-pinned sockets and refuses redirects; Cloudflare-hosted external peers remain subject to the platform raw-socket limitation, while tenants on the same hosted deployment use the internal Durable Object route.
- **Wake settings API.** Control-core accepts encrypted signing secrets and an optional tested configuration version. Blank secrets are reused only for the same destination and authentication mode; removal clears wake credentials. Existing ciphertext remains compatible. Failed wake pushes retain the outbox without logging provider error text.
- **OpenBot signing and replay.** The Worker refuses unsigned OpenBot wakes. Setup docs explain timestamp checks, per-attempt delivery IDs and task-level retry idempotency. Hosted OpenBot evidence is scoped to webhook wakes; self-hosted 0.8.19 retains its pairing/messaging/wake evidence.

- **Setup feedback (#148).** The setup skill has a "When something goes wrong" section: after a failed setup step, the agent offers to file a redacted public report with `feedback`, `send_feedback`, or the a2a.exposed feedback form, and sends it only after the human agrees.
- **Hosted OpenBot tested.** The compatibility table and OpenBot setup docs list hosted OpenBot wakes at a2a.exposed as tested end to end.
- **OpenBot tested (#143).** Mark OpenBot tested end to end on self-hosted 0.8.19: pairing, messaging, and webhook wakes with the `openbot` preset.
- **Setup consent and hosted option (#148).** Require explicit human consent to the account and resource plan before Cloudflare changes; offer the free hosted agent option up front, with dashboard and MCP setup guidance.

## 0.8.13 – 0.8.18

`npx -y a2a-exposed@latest deploy` (applies migrations `0009_outbound_seen`, `0010_conversation_peer`, `0011_conversation_owner`, and `0012_conversation_peer_owner`: an outbound reply stays in the inbox until that list is read, a wake is keyed by peer and conversation, and each peer has its own row for a context id).

- **A2A version (#131).** `A2A-Version` (the header, or the `A2A-Version` query parameter when the header is absent) selects the 0.3 or 1.0 response shape, including when the method name belongs to the other version. A patch suffix is ignored. With no header and no query parameter, the method name still selects the shape, so a 0.3 client that omits the header keeps a 0.3 answer and a headerless `SendMessage` stays 1.0. An unsupported version is `-32009` before method lookup. The façade forwards a declared version to the upstream as the `A2A-Version` header. A call with no header and no query parameter stays headerless, so the upstream still chooses from the method name.
- **Extended agent card (#131).** `GetExtendedAgentCard` and `agent/getAuthenticatedExtendedCard` return `-32007` in inbox mode and on the façade.
- **init and a cf profile (#131).** When `--cf-profile` is set and `cf auth whoami` lists no accounts, `init` reads `cf accounts list` and saves the account when that list has exactly one. Several accounts still need `--account-id`. An API token with no profile still asks for User → Memberships → Read.
- **Inbox pages.** `GET /owner/inbox` returns one page of tasks, oldest first (default 200, `limit` 1–200). The next page's cursor is the `x-a2a-next-cursor` header. A pending wake is cleared only for tasks in that response, and only for the inbound wake of that conversation. Tasks that are not in the response keep their pending wake. An outbound update that reuses the task id keeps its pending wake. Marking a task working, or replying, clears the inbound wake for that task and that conversation. `inbox` follows every page. Past 10000 pages it exits with an error instead of a short list. The MCP `inbox` tool returns one page (default 20) and says when to call it again with the cursor.
- **Public addresses.** An IPv6 wake or client-metadata target is parsed and allowed only in global unicast (2000::/3), outside IANA special-purpose blocks that are not globally reachable. Benchmarking (2001:2::/48), Teredo, 6to4, and documentation ranges are refused.
- **Peer conversations (#132, #135).** History and wakes stay scoped by peer and `contextId`. Claiming a conversation and storing the first task are one transaction. `conversation_owners` is one row per peer and context id (`0011_conversation_owner`, then `0012_conversation_peer_owner`). The task is written only when this peer's owner row is present. One peer's history and wake are not written into the other's. Migration `0010_conversation_peer` is the wake key. The façade's context check is unchanged: an unrecorded context is still `-32602`, and the façade does not mint a replacement id. Outbound send and reply are unchanged.
- **Client context ids (#135).** A2A lets an agent accept a client-supplied `contextId`, and forbids minting a replacement when it will not. This inbox accepts the id for the caller. An id this peer already holds continues that conversation. An id this agent has never seen, and an id another peer already holds, are the same for the caller: a new conversation of their own, and the response echoes the supplied id. The other conversation's tasks, text, and wake are not returned. `ListTasks` for a context this peer has no tasks in is empty whether or not another peer uses that id. Omitting `contextId` still starts a server-generated conversation. `GET /owner/history/<id>?from=<peer>` and `GET /owner/inbox?from=<peer>` read one peer. The wake hint includes `--from`.
- **ListTasks pages (#136).** `ListTasks` returns a cursor in `nextPageToken` (empty on the last page). Tasks are newest status timestamp first, then id. `pageSize` is 1–100 (default 50). The list is the caller's tasks. `totalSize` counts every match. A bad `pageToken` is `-32602` and the error does not echo the token.
- **Push config list and delete (#136).** The inbox accepts `ListTaskPushNotificationConfig`, `ListTaskPushNotificationConfigs`, and `DeleteTaskPushNotificationConfig`, and the 0.3 methods `tasks/pushNotificationConfig/list` and `tasks/pushNotificationConfig/delete`. They apply to the configs stored on that task and only for the calling peer. Another peer's task is `-32001`. Delete of a missing config on an owned task succeeds. A missing id is `-32602`. The 1.0 list is `{ configs, nextPageToken }`. The 0.3 list is the array. The façade still refuses push (`-32003` after the per-peer task check).
- **Outbound replies (#129).** The hosted owner RPC accepts `PUT /owner/outbound-peers/<alias>` with `{ url, token }`. The token is sealed in the owner handler and is not logged or returned. Connector `send` registers a push to this A2A endpoint's `POST /push` only when the peer card advertises `capabilities.pushNotifications`. Otherwise the send omits the push config and the reply is read with `poll_outbound` (`tasks/get`). The push token's hash is stored before the send, so a callback that arrives first still authenticates. Only the hash is stored. The peer's reply is recorded in that conversation's history and listed on the first inbox page until that list is read. Marking it seen matches the update snapshot that response returned, so a newer push stays unseen. A `message` or `artifactUpdate` push supplies that text. A follow-up keeps the same conversation id. A call to another tenant on this deployment's domain uses the tenant directory and an internal Durable Object fetch. A public peer stays a public HTTPS call. Self-hosted Workers and the CLI are unchanged: `peers sync` still uses the owner token, and CLI `send` still registers a push only with `--push`.

- **HTML landing page at `GET /`:** a browser gets a small page with the agent name, description and skills (from the served card, so in proxy mode the rewritten one with no private URL), the note that this is an A2A endpoint, and links to the agent card and the `/device` pairing page (or a note when pairing is off). It has the same frame as `/device`: no scripts, no external assets, a strict nonce CSP. Requests without `Accept: text/html`, or with `?format=json`, still get JSON, now with `description`, `a2a` and `pairing` alongside `name` and `agentCard`.
- **Tailnet agents pairing out:** `connect --card-url <url>` names your card in the pairing request. A private https card (`*.ts.net`, LAN) is sent as informational: the other inbox's `/device` page and wake (`agentCardPrivate: true`) flag it as "not publicly reachable". A non-https card is still left out.
- **Docs:** setup skill section "Already have A2A on a Tailnet or LAN: expose it through a public façade" (tunnel + Access recipe, deploy, card rewrite rules, upstream credential model, threat model), README section and security/protocol notes, new troubleshooting rows, `deploy.env.example`.

## 0.3.1

- **Stale peer-token variables:** a peer token in the environment (`PEER_<ALIAS>_TOKEN`, a `--token-env` variable, or `A2A_PEER_TOKEN`) still overrides the one saved in `config.env`, but when both are set and differ, `send`, `poll`, `connect` and `peers add|list` now warn on stderr, naming the variable and how to clear it (`unset PEER_<ALIAS>_TOKEN`), never either value. `connect` (and `peers add --token-stdin`) also warns right after saving a new token that a stale variable would still win on the next `send`; `connect --json` adds `env_overrides_token: true`.

## 0.3.0

Upgrade: `npm i -g a2a-over-webhook@latest`, then `a2a-over-webhook deploy` (applies D1 migrations `0002_wake_budget.sql` and `0004_pairing_replace.sql`).

- **Password setup over the web (`pair set-password --web`):** the CLI asks the Worker for a one-time link (`POST /owner/pairing/password-link`, default 15 minutes, configurable 1–60). The human opens `/device/setup?t=...`, types a password (≥12) twice, and the Worker hashes it with PBKDF2-SHA256. The link is single-use, burned after 5 bad attempts, and a new link invalidates the old one. Same CSP/CSRF as `/device`. `status` / `pair list` show when the password was set and how (`web` or `terminal`). Agents must send the link to their human and never open it.
- **Re-pairing without orphan tokens (F6):** `connect` refuses an alias whose token still works, unless `--replace` (alias `--force`). With `--replace` the old token is presented on `device_authorization`; the Worker stores `replaces_label` (D1 migration **`0004_pairing_replace.sql`**, applied automatically by `deploy`) and the presented token's hash (`replaces_hash`), and, on approval, swaps the token under the same label only if that exact token is still on the label (a rotate or revoke in between downgrades to a new label, so a leaked old token can't take over a rotated one). Older peers keep the old token until their owner revokes it; the CLI says so. Revoked labels are not reused.
- **Expired `--no-wait` resumes (F7/F8):** resuming an expired request exits 1 with "expired before it was approved; nothing was stored" and prints the exact re-run command (every flag, including `--alias`). Never starts a silent new request.
- **Polling agents see pairing requests (F5):** `inbox` lists pending pairing requests after the tasks (and on stderr with `--json`); the polling recipes (Hermes, OpenClaw, generic) tell the agent to relay the code and never approve. `pair set-password` no longer claims every wake carries the link.
- **Node 22 and CLI upgrades (F1–F3):** the setup skill and the CLI's version error list mise / nvm / fnm / the official installer. The install recipe is `npm i -g a2a-over-webhook@latest` (the old `command -v || npm i` never upgraded). An outdated notice on stderr checks the npm registry at most once a day in a detached process (`A2A_NO_UPDATE_CHECK=1` / `DO_NOT_TRACK=1` / `CI` opt out). Skills and `cli/package.json` versions are kept in sync with the release.
- **Deploy / status friction (F4, F16–F18):** `init`/`deploy` wait until the agent card is served twice in a row (Cloudflare 1042 while a new workers.dev Worker propagates). `status` names Cloudflare error codes and treats 1042 as "retry in 30 s". Optional hints (`also:`) keep the next-step line short; with no wake it no longer mentions a preset. Global `--config-dir` (and `--worker-dir` for the Worker project; `--dir` still works). `url` exits 1 when unset. `connect --json` uses `not_waiting` instead of `started`. Friendly 401 from `send`/`poll`. `--workers-logs on|off` enables persisted Workers Logs (query strings redacted). Teardown steps are documented (no command).
- **Auth and pairing polish (F9–F15):** 401 echoes the JSON-RPC `id`; `WWW-Authenticate` carries `resource_metadata` (RFC 9728) and a different `error_description` for a bad token vs no token; `/.well-known/agent.json` is an A2A 0.3-shaped card; `token revoke` of an unknown label exits 1 with a clear message (text, not raw JSON); `pair approve` in human mode names `deploy --pairing-approval agent`; Deny on `/device` needs no password and never runs PBKDF2; pairing `off` lists no pending requests; expired device codes return `expired_token` for 24 h, then `invalid_grant`.
- **PBKDF2:** default stays 100,000 (Workers maximum); range 50,000–100,000 via `init`/`deploy --pbkdf2-iterations` (`A2A_PBKDF2_ITERATIONS`). Each stored hash keeps its own count. Documented in the threat model (online guessing is limited by lockouts; lower only if `/device` hits Cloudflare error 1102 on the free plan).
- **Worker:** migration `0002_wake_budget.sql` creates the `wake_budget` table on D1 databases whose `0001_init.sql` came from an earlier build (D1 tracks migrations by file name, so the current `0001` never ran there). Without it, messages to such an inbox failed with `-32603 Internal error` and sent no wake. It does nothing on newer databases, and `deploy` applies it even where `0003_device_pairing.sql` is already recorded (cf applies every unrecorded file in numeric order). A new test replays these upgrades.
- **Docs:** setup skill section on adopting an existing deployment (same Worker, D1 and hostname) without reissuing tokens or re-uploading secrets: `deploy` keeps the Worker's secrets and applies `0002`–`0004`, then `status` checks the result. Device-flow pairing is on after the deploy (`human` approval), or `--pairing-approval off`.
- **Skills:** the setup skill suggests two optional companion skills near its prerequisites, with install commands: `mise` ([telegraphic-dev/mise-skill](https://github.com/telegraphic-dev/mise-skill), for Node 22.18+) and `cloudflare` ([cloudflare/skills](https://github.com/cloudflare/skills), for Workers, D1, the `cf` CLI, DNS, Tunnel and Access). The operate skill points to `cloudflare` for Cloudflare-side troubleshooting. `related_skills` lists them; the README's install section names both.

## 0.2.0

- **Tunnel on a workers.dev inbox:** `tunnel create` (and `init --workers-dev --tunnel`) no longer needs a custom inbox hostname. The wake hostname goes on any zone of the account: the inbox hostname's zone, otherwise the account's only zone (it says which it picked). With several zones it stops and lists them; choose with the new `--tunnel-zone <zone>` (or `--tunnel-hostname`). With no zone it says plainly that polling is the option. Zones are listed for the deployment's account only.
- **`status` command:** a read-only summary of the deployment and base URL, an agent-card check done by the CLI (no `curl`), the wake mode (webhook, tunnel, or none, which means polling), the tunnel state and connector connections, and a `next step:` line. Exit code 1 when something is broken. `init` and the card warning now point to it.
- **Safe re-runs:** `tunnel create` on an existing tunnel creates nothing. It re-uploads Worker secrets if they're missing, together with an exported `WAKE_WEBHOOK_KEY` / `WAKE_HMAC_SECRET`, and warns if the Worker would still have no webhook auth. A missing connector token file is downloaded again. When an earlier run stopped halfway, it asks for `tunnel rm`. `status` flags a local preset (Hermes, OpenClaw) whose Worker sends no webhook auth. If `init --tunnel` fails at the tunnel step, it says the inbox is deployed and how to continue.
- **Setup skill:** decide how wakes reach the agent (public webhook, local-only webhook, or none) before picking the inbox URL. For local-only webhooks, check for a zone and recommend the secure tunnel with either inbox URL, explaining the tradeoff to the user; polling is the fallback. Adds copy-paste polling commands for Hermes (`hermes cron create "every 2m" ... --skill a2a-over-webhook --name a2a-inbox`, checked against the Hermes source and docs) and OpenClaw (`openclaw cron add --every 5m --session isolated ...`), with a note about command approval prompts. Also adds resuming with `status`, moving from polling to the webhook without a redeploy, and new troubleshooting rows.
- **The agent card always advertises the public base URL:** the Worker template no longer reads an `A2A_PUBLIC_URL` override from the deploy environment, so a local webhook, Tailnet or tunnel URL exported by the agent can't end up in the card. The card URL comes only from the custom hostname or the workers.dev URL. The Worker also ignores a non-https or private-network `PUBLIC_URL` and falls back to the request origin. `init` and `deploy` verify and print the deployment's own URL, and warn when an exported `A2A_BASE_URL` differs. They also warn when the card points elsewhere. `status` flags both cases (`agent card: WRONG URL: ...`, next step `deploy`). This was found in a Hermes setup where the card advertised a Tailnet URL and the agent fixed it by hand.
- **Device-flow pairing (OAuth 2.0 Device Authorization Grant, RFC 8628):** agents connect without exchanging tokens in chat.
  - Each inbox serves `POST /oauth/device_authorization`, `POST /oauth/token` (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`, `invalid_grant`), a `/device` approval page, and `/.well-known/oauth-authorization-server`. An approval issues a normal hashed `a2aow_` peer token, single-use.
  - Approval is `human` by default: an approval password set with `pair set-password` (terminal only, no echo; stored as salted PBKDF2-SHA256), with lockouts. `--pairing-approval agent` adds `pair approve <code>`; `off` disables pairing.
  - New requests wake the agent with `kind: "pairing_request"`. New commands: `connect <url>` (client; `--no-wait`, `--json`), `pair list|approve|deny`. `token list` shows tokens created by pairing.
  - The agent card advertises an A2A 1.0 `oauth2SecurityScheme` with a `deviceCode` flow next to `bearer`, and a 401 from the A2A endpoint explains the flow.
  - Flood limits apply per IP and globally. D1 migration `0003_device_pairing.sql` (numbered to avoid a `0002` from another branch); run `deploy` to apply it.
- **Docs:** both skills and the README check the endpoint with `status` instead of `curl`, because some agent sandboxes (Hermes) flag `.dev` URLs in shell commands. The README and the operate skill describe the tunnel as needing any zone on the account.

## 0.1.0

First npm release of the CLI (`npm i -g a2a-over-webhook`).

- **Worker:** public agent card and A2A JSON-RPC endpoint (1.0 primary, 0.3 compatible) with a D1 inbox; per-peer `a2aow_` bearer tokens stored as SHA-256 hashes; push notifications; per-conversation wake debounce and an hourly wake cap.
- **Wake presets:** `grok-bot`, `claude-code`, `openclaw-wake`, `openclaw-agent`, `hermes` (HMAC-SHA256), `generic`; `wake set|unset|test|preview|fingerprint` with masked previews and SHA-256 fingerprints instead of secret values.
- **Deploy:** `init` / `deploy` with the `cf` CLI, on a custom domain or a free `*.workers.dev` URL (`--workers-dev-subdomain` registers the account subdomain); `deploy --workers-dev` / `--hostname` move a deployment between the two and retire the old URL (301 for the card, 410 otherwise).
- **cf auth profiles:** `--cf-profile` / `CF_PROFILE` for several Cloudflare logins on one machine.
- **Secure tunnel:** `tunnel create|status|rm` publishes a local-only webhook (OpenClaw, Hermes) through a named Cloudflare Tunnel behind a Cloudflare Access app that admits only the Worker's service token.
- **Inbox and outbound:** `inbox`, `show`, `working`, `reply`, `history`, `contexts`; `peers add|list|rm`, `send`, `poll`, `outbound`; `token issue|list|revoke|rotate`.
- **Skills:** `a2a-over-webhook-setup` (deploy and wake configuration) and `a2a-over-webhook` (day-to-day), with Hermes and OpenClaw frontmatter metadata.
- **Release tooling:** CI on pushes and PRs; tag-triggered npm publish with provenance and a GitHub release.
